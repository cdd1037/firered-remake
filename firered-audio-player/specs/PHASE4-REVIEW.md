This is a code/artifact review plus independent bounded decoding and runtime regression checks. It is not listening approval, target-device testing, or a second full 386-species render run.

## Decision

Do not promote this to 386-species public runtime support or universal original-driver waveform fidelity. The ordinary runtime API remains Charmander normal only.

## Isolation and bounds

`CRY_COVERAGE_RESEARCH` is defined only in `research/CryCoverage.csproj`. That project explicitly compiles the existing engine sources with its own `ResearchCry.cs`. The production core project has an explicit source list excluding the research file; the ordinary CLI project also excludes it by directory.

The sole functional `Synth.cs` hook is conditional. Without that symbol, the original compressed-sample restriction and `PrepareNormalCry` path remain. `NormalCharmanderCry.Build` still rejects any species other than4 and any mode other than0. A metadata-name check of the current core and CLI assemblies finds neither `StartResearchCry` nor `researchSamples`; both are present only in the research assembly. Changing the class declaration to `partial` does not itself expose another method.

Research predecodes one selected source before rendering and injects that sample into the existing live PCM renderer. It does not load a reference WAV, catch a rendering failure and substitute recorded audio, or install an alternate synth. No new runtime dependency was added.

The strict shared `DpcmDecoder` is unchanged. It retains its decoded-sample budget, required-payload calculation, resource-span validation, and explicit truncation failure. Dynamic sequence bounds and relocation are unchanged. The research code receives a hash-pinned original resource pack through `Resources.FromPack` and uses manifest-specific physical payload lengths.

The guard extension is explicit and isolated: **196 stored guards,190 reconstructed guards**. For a manifest-marked missing guard, research decodes only the playable sample count and appends one copy of the final sample. The inventory proves that value against the source WAV and the original following ROM byte's zero high-nibble delta. It does not silently overread alignment or the next asset. The harness also confirms that the unchanged strict phase3 decoder rejects those190 guard-inclusive requests and accepts the other196.

The manifest is trusted research input regenerated by `verify-phase4.sh`, rather than a new general-purpose user-input format. `StartResearchCry` accepts the supplied tone/payload/guard metadata; it does not independently authenticate every manifest field or implement a production species API. It is exercised on a fresh synthesizer per render. Retrigger, cancellation, multi-cry overlap and BGM/SE coexistence for all386 species are not established by this batch.

## Quantitative limits

The six sampled original-driver comparisons all use the same single onset crop:855 frames removed from the reference, estimated from its first second and then held fixed. Correlation spans **0.9860036–0.9968761**, and PCM16 RMSE spans **97.51–205.00**. All six are explicitly non-exact. The analysis makes no gain fit, time stretch or per-note alignment. These results support representative similarity, not complete-library fidelity or hardware bit perfection.

The recorded batch took **8.6496196s**, reports1,276,327,448 total allocated bytes and66,928,640 working-set bytes. These include the offline harness, repeated output buffers, hashes and two renders per species; they are not per-cry shipping costs.

Most measured render loops reported zero current-thread allocations, but **three of772 passes did not**:

- Forretress: second pass2808B
- Solrock: second pass2984B
- Slaking: first pass6272B

The exact cause was not diagnosed in this review. It is incorrect to call the complete phase4 batch allocation-free. The separate existing prepared-Charmander allocation self-test still passes; that narrower test does not erase these observations.

## Non-blocking harness hardening

Two small issues do not invalidate the present artifacts but should be addressed before treating the harness as a durable general regression gate:

1. It checks `Ended`, `Clipped` and nonzero peak explicitly on the first pass only. The second pass's PCM hash is compared, but its final state is not independently asserted or recorded. Check both states when extending the gate.
2. `success++` occurs before a representative WAV write. A later write exception could leave a failed row while the success counter still includes that species. All six current files exist and match the expected hashes, so this path did not corrupt the reviewed run. Increment success only after all per-row work succeeds.

No runtime code was edited during this review.
