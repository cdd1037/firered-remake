# 当前实施顺序

当前优先任务是工程治理，工作在refactor/project-governance；不自动把治理授权扩大为玩法修改或新内容开发。完整产品目标见[范围](scope.md)，已实现与缺口只维护在[当前状态](first-clear-remaining-scope.md)。

## 1. 工程治理

按[质量审核](project-quality-review.md)分小批实施：

1. 日常Hash/日志负担、保存反馈、真实资源再生断链、当前说明与测试慢因。
2. 内容表单一权威、普通菜单语义、实际遇敌表和导入共用层，降低增加原作内容的跨层修改成本。
3. 一个桌面目标的独立测试包、启动/加载/资源生命周期，以及有实际修改需求的控制器边界。

每批只跑受影响的规则/导入/应用/原生冒烟；跨边界批次完整回归。按实际耗时优化测试，不删除独立数值oracle或用静态源文本检查冒充C#行为测试。

## 2. 后续产品内容

恢复内容开发时，以当前范围页的真实缺口安排，先补原作可达地区、交互与养成闭包，再逐步补菜单、中文和专属表现。不要依据历史阶段页重新实现已经接通的主线/七岛/双打。

专属动画与真实视听检查分开推进；不要求每个重复动画单独开新工程验收，也不把通用表现称为原版专属还原。P0真实音频尚未关闭，不应伪造听感结果。

未批准的规则变化、通信进化服务具体方案等仍需用户决定。工程重构应保持原作语义和已批准差异。

## 3. 提交与交付

小批代码按当前授权同步治理分支，不改main。Drive完整工程包按用户指定节点处理。普通工程、源码Git与必要私有资源的边界保持清楚；不能把当前未闭合再生的generated全部视为可删缓存。

备份不要求再次搭建整份恢复环境或重放历史路线。交付说明写清实际构建、测试、原生验证和未覆盖边界，不累计历史通过次数，不以代码量/测试数推算游戏完成率。
