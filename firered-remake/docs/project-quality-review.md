## 结论

项目已有值得保留的规则底座，但仍带有明显的阶段式研究工程结构。上一轮目录、重复数据和运行元信息治理有真实收益；它不代表内容编辑、日常运行、独立交付和长期维护已经全部收口。

不建议推倒重写、换引擎或引入企业级框架。下一步应按实际风险修少量关键边界：

1. 日常命令不再承担全状态取证成本；保存失败要准确可见。
2. 修复真实的资源再生断链，补齐普通启动与一个桌面目标的交付路径。
3. 将原版一致性验证与运行时内容合法性分开，降低新增地图/服务的跨层修改成本。
4. 保留高价值测试，补真正的行为和引擎边界；维护唯一可信的当前说明。

P1 表示下一轮对应工作必须处理，具体注明是日常运行、再生、交付还是恢复风险；不表示所有问题都是当前玩法错误。P2 是长期维护/扩展前应处理的问题，P3 是有条件再做的收尾。

## Q01 · P1：日常运行承担了不必要的全状态成本

**证据**：`src/Game.Application/CommandSession.cs:29–43` 对成功、拒绝和故障都计算完整 `CanonicalJson.Hash`；`CanonicalJson.cs:8–26` 包含全量序列化、排序、复制。`src/Game.Godot/CampaignView.cs:425–432` 在普通命令前还可能 flush 一次 play-time 命令。`CampaignSlotMachineView.cs:45–56` 每个 60Hz 逻辑帧执行 slot_tick。

默认 `scripts/dev/launch-current.sh:9–13` 又无条件开启 FIRERED_EVIDENCE。`CampaignView.cs:432,579–580` 对非老虎机命令序列化并同步写完整状态；老虎机日志是摘要，不能误说它也逐帧写完整状态。文档要求普通游玩关闭详细取证，与启动器不一致。

**实际量级**：315,347 字节终档的一次全状态 Hash 分配约 5,489.94 KiB。两次小探针约 13–22ms/次，受 Debug/tiering 等影响，不作为帧时间结论。按每秒 60 次线性估算的约 322 MiB/s 分配只是理论放大量。

历史也会增长：`CampaignWildBattles.cs:256–270` 永久追加已结算野战记录；`CampaignExploration.cs:71` 要求下一个 ID 等于全部历史长度加一，并扫描完整历史。当前 634 条野战记录占 131,710 字节。187 条训练家历史没有复制完整静态定义，不应机械删除。

**建议**：核对 StateHash 消费者后，完整 Hash 留在保存、显式回放/诊断边界；日常事务继续使用不可变状态和 revision。默认关闭全状态 evidence。随后把普通已结算记录归约为真实需要的统计、ID及被业务引用的 receipt，开发日志独立保存；不恢复任意 256 条环形证明，也不先换二进制存档。

**验收**：同一真实存档下移动、静止、老虎机各做短采样；普通操作无全状态日志，存档完整性检查仍有效，游戏结果/RNG不变。

## Q02 · P1（玩家测试包前）：保存失败反馈不可靠

`CampaignView.cs:405–418,523–534` 的普通野外 F5/F9 错误主要写 `_status`，没有通用可见错误显示。`CampaignFieldMenuView.cs:226–233` 把保存失败统一说成 “Return to a stable field.”，无法区分权限、磁盘、损坏或当前事件禁止。此为代码确认的反馈缺口，未破坏真实存档做 GUI 实验。

## Q03 · P1（再生）：一个文档推荐的导入器会成功产出空表

`scripts/imports/maps/import-field-tilesets.py:23` 仍只扫描名为 runtime-map.json 的地图；当前已是 schema3 的扁平地图文件，旧文件名数量为零。`:37` 仍写 generated/field-tilesets.json，而 `src/Game.Content/GeneratedFieldTilesets.cs:20` 读取 maps/tilesets.json。

**实际复现**：在临时目录复制当前地图 JSON 和原始 layouts 输入后，现有命令退出码为 0，却报告 layouts=0、tilesets=0、bytes=29，产出两个空字典；运行时预期路径不存在。当前正确资源是 246 layouts / 45 tilesets，因此当前游戏仍能使用保留产物，但重新生成这一步会断链。

**建议**：按实际地图 schema/加载索引选图，输出统一当前路径；空有效输入明确失败。加入一个最小真实地图再生→实际读取器的闭环。不要用一个新的固定 246/45 门槛替代这个错误。

## Q04 · P1（独立交付）：开发工程还没有普通游戏包入口

**验收**：把包移出工程目录，去掉开发环境变量后启动、新游戏、保存、退出、Continue；不能借用原工作树素材。真实音频输出仍需单列验证。

## Q09 · P2：拆成 partial 文件尚不等于模块所有权清晰

## Q10 · P1（恢复）/ P2（维护）：生成资源目前不是可随时删除的缓存

缺8份逻辑音频cue输入；cry目录构造还读已缺失的 phase4/inventory.json，而其旧生成链要求 .gba/.map/.elf。Celadon approach encounter缺现存producer。音频pack从零构造要求现有pack或合法自备ROM，不能把所有再生都描述成只需pret raw。

## Q11 · P2：测试需要补覆盖边界，不需要再大规模瘦身

2,606是测试用例数，不是功能完成率。其中1,416条招式行验证公共回合可完成，只需MoveUsed或PP事件，不能代表每个招式效果正确；但它们合计仅5.49秒，值得保留。独立数值JSON/CSV约451KB，无字节重复，不应为了体积删oracle。

主要缺口：
- Presentation的12项只链接两类纯C#代码，没有执行Godot纹理消费者和实际UI；此次原生检查发现并修复的border/继承副本错误说明该边界重要。
- FanClub等服务的原C字符串/Load检查未覆盖C#实际玩法；例如12小时衰减应有可读边界用例。
- 三个已有图像/图集脚本未接ResourceImport默认入口。本轮定向运行5+8+1项全部通过，成本很低。
- 多个应用用例依赖一份后期存档及私有反射准备；generated-only新游戏用例也与该后期存档绑在一起。

**建议**：接入已有14个快检查；各受影响效果族补成功/失败前提和可观察结果；加小型真实Godot冒烟（输入帧、菜单、warp、战斗返回、存读）。基础新游戏和后期Continue测试分开。保留数值向量与快速全招式冒烟，不逐招式人工验动画，不恢复72个历史测试工程。

## Q12 · P2/P3：加载、保存与资源生命周期需要有针对性的收口

首屏前同步加载全地区表现，冷地图还可能在_Draw恢复纹理。保存最多重复多次全状态解码/语义验证；仅内存storage探针也分配约33MiB，不能当真实磁盘耗时。合成音频在同一主线程补约106.7ms队列，长阻塞存在断音风险，本次未听测。

入口对超限存档仍先全文件fingerprint，绕开16MiB读取保护的性能目的。地图3张/24MiB仅是map-owned逻辑RGBA预算，pin可超，不是全局VRAM上限；若干字体/皮肤有Dispose但未覆盖_ExitTree，尚无证据称永久显存泄漏。

**建议**：优先Q01，再去可证明等价的重复解码；显示启动阶段，按真实地图/场景需要加载表现。补齐已有对象所有权和释放，区分主线程Godot操作与纯文件处理。不要先加大全局缓存、盲调音频缓冲或贸然异步化全部游戏规则。

## Q13 · P2/P3：少量治理基础设施缺口

保留标准dotnet build/test、当前.NET/Godot明确版本策略和8测试项目。Python/Pillow缺可安装的简洁依赖清单，建议一份小requirements与已测组合；可选音频研究依赖单列。

源码与私有素材分离方向正确，但公开前仍需作者许可选择、第三方/原作片段及字体说明的定向复核。现为私有研究，不以此阻止开发，也不作法律结论。浅克隆范围的secret扫描没有高置信命中，不能代表所有历史已审。

暂不急于复杂CI。先让一个本地命令能做有价值的构建/测试、一个命令启动普通游戏、一个桌面测试包可独立运行；之后再接一个平台的轻量CI。明确私有素材输入，不能为CI把它们强制塞进Git。
